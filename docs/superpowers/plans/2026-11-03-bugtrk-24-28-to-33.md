## BUGTRK-29: Delete a done card's attachments after 7 days

**Rule:** a file is deleted once both its card's `completed_at` and its own `created_at` are more than **7 days** old. A file added to an old done card still gets its own 7 days. Reopening clears `completed_at`, which stops the clock. This covers every way a card becomes done:

- edits and bulk edits
- board drags
- status category changes
- imports
- the bots and the MCP tools

That's because the job reads only `completed_at`, never a code path.

**Migration `023_attachment_retention.sql`:**

```sql
ALTER TABLE attachments ADD COLUMN purged_at timestamptz;
CREATE INDEX tasks_done_with_files_idx ON tasks (completed_at) WHERE attachment_count > 0;
```

**Purged rows become tombstones.** The row stays with `purged_at` set, so inline `![…](/api/attachments/<id>)` images keep resolving. Only the file goes. `attachment_count` counts live files only.

**Shared:**

- `ATTACHMENT_RETENTION_DAYS = 7`.
- `fileDeletesOn(completedAt, createdAt)`.
- `Attachment.purgedAt`.

**Server (`modules/attachments`):**

- `PURGE_DONE`, one statement:

  ```sql
  WITH purged AS (
    UPDATE attachments a SET purged_at = now() FROM tasks t
    WHERE a.task_id = t.id AND a.purged_at IS NULL AND t.attachment_count > 0
      AND t.completed_at < now() - make_interval(days => $1)
      AND a.created_at < now() - make_interval(days => $1)
    RETURNING a.task_id, a.storage_key
  ), counted AS (
    UPDATE tasks t SET attachment_count = t.attachment_count - p.files
    FROM (SELECT task_id, count(*)::int AS files FROM purged GROUP BY task_id) p WHERE t.id = p.task_id
  )
  SELECT DISTINCT storage_key FROM purged
  ```

  Then `removeUnreferenced(keys)`. `purgeDoneAttachments()` joins the hourly `purge()` in `server/src/index.ts:18-26`.
- `UNREFERENCED_KEYS` only counts live rows (`AND purged_at IS NULL`). A duplicate or the next repeat that still uses the same file keeps it.
- `DELETE_FILE` returns `purged_at`, and `BUMP_COUNT` runs only for live rows. Removing a tombstone doesn't lower the count twice.
- `COPY_TEXT_FILES` / `REWRITE_TEXTS` carry `purged_at` over, so duplicates of a purged card keep the placeholder. The `files` count covers live copies only.
- `FILE_KEYS` in `tasks/service.ts:154` skips purged rows.
- `GET /attachments/:id` for a purged file:
  - An image gets a small inline SVG with the text "Image deleted" and "7 days after the card was done", as `image/svg+xml` with a long cache.
  - Any other file gets **410** "Deleted 7 days after the card was done".
- `toAttachment` adds `purgedAt`.
- The board cover (`tasks/queries.ts:76-78`) skips purged files.

**Client (`AttachmentsSection.tsx`):**

- On a done card, each live file shows "Deleted on <date>".
- A single banner reads "Files are deleted 7 days after the card is done. Reopen it to keep them."
- Purged files are listed greyed out, "Deleted on <purgedAt>", with no download. The tombstone can still be removed.

**Tests:**

- `server/test/attachmentRetention.test.ts`:
  - A file is purged 8 days after done; it stays at 6 days.
  - A reopened card keeps its files.
  - A recent upload on an old done card stays.
  - A shared file survives while a duplicate is live.
  - Counters stay consistent, including after removing a tombstone.
  - Image → SVG placeholder (200); PDF → 410.
  - Storage removal is checked on disk.
- Update `expectCountersConsistent` (`taskDepth.test.ts:13-35`) to count live rows.
- Shared test for `fileDeletesOn`.

## BUGTRK-24: "Who can see" on card types, and the Conclusions tab

### Part 1: Card-type visibility

**Rule:** a member sees a card when any of these holds:

- it has no custom type;
- its type's `view_role_ids` is empty;
- their role is in `view_role_ids`;
- they are the project owner;
- they are the card's assignee or reporter.

A role that can create or edit a type must also be able to see it.

**Migration `024_card_type_visibility.sql`:**

```sql
ALTER TABLE project_card_types ADD COLUMN view_role_ids uuid[] NOT NULL DEFAULT '{}',
  ADD CONSTRAINT project_card_types_view_roles CHECK (
    view_role_ids = '{}' OR (create_role_ids <> '{}' AND create_role_ids <@ view_role_ids
                             AND edit_role_ids <> '{}' AND edit_role_ids <@ view_role_ids));
```

- The CHECK guards partial PATCHes too. The error handler turns it into `400 Roles that create or edit X cards must be able to see them`.
- Deleted roles stay in the arrays as dangling ids, as they do today. A dangling id matches no one, so visibility stays closed rather than opening up.

**Written once:** `server/src/modules/cardTypes/visibility.ts` exports `visibleTo(task: string, user: string)`. It returns a self-contained SQL predicate that needs only the task alias, so it fits any query (cards, stats CTEs, activity, calendar, export, bots):

```sql
(${task}.card_type_id IS NULL OR ${task}.assignee_id = ${user} OR ${task}.reporter_id = ${user}
 OR NOT EXISTS (SELECT 1 FROM project_card_types vct WHERE vct.id = ${task}.card_type_id AND vct.view_role_ids <> '{}'
   AND NOT EXISTS (SELECT 1 FROM project_members vm JOIN projects vp ON vp.id = vm.project_id
                   WHERE vm.project_id = ${task}.project_id AND vm.user_id = ${user}
                     AND (vm.role_id = ANY(vct.view_role_ids) OR vp.owner_id = ${user}))))
```

The `card_type_id IS NULL` check short-circuits almost every row, and `tasks_card_type_idx` covers the rest.

- A `NULL` user, used for bot group chats whose audience is unknown, sees only unrestricted cards.
- It works across projects too: search, dashboard and my tasks.

`LOAD_TASK` (`tasks/access.ts:39-48`) already joins `m` and `ct`. It adds the same rule inline, so a hidden card is a **404** everywhere a task is loaded:

- detail and full page
- comments, attachments, checklist and relations
- reopen, move and duplicate
- MCP `fetch` and `update_task`
- bot `KEY-12?` and `done`

It also returns `restricted` (`ct.view_role_ids <> '{}'`) for the bot group-chat rule.

## BUGTRK-32: Shared bot engine + Discord

**Why it has to be shared:** the notifier claims activity, overdue alerts, reminders and the outbox once, destructively (`notifier.ts:102-168`). A second notifier would steal the first one's alerts.

**Migration `025_bots.sql`:**

```sql
CREATE TYPE bot_platform AS ENUM ('telegram', 'discord');

ALTER TABLE telegram_chats RENAME TO bot_chats;
ALTER TABLE bot_chats DROP CONSTRAINT telegram_chats_pkey,
  ADD COLUMN platform bot_platform NOT NULL DEFAULT 'telegram',
  ALTER COLUMN chat_id TYPE text;
ALTER TABLE bot_chats ALTER COLUMN platform DROP DEFAULT, ADD PRIMARY KEY (platform, chat_id, project_id);
ALTER INDEX telegram_chats_project_idx RENAME TO bot_chats_project_idx;

ALTER TABLE telegram_link_codes RENAME TO bot_link_codes;
ALTER TABLE bot_link_codes ADD COLUMN platform bot_platform NOT NULL DEFAULT 'telegram';
ALTER TABLE bot_link_codes ALTER COLUMN platform DROP DEFAULT;

ALTER TABLE telegram_outbox RENAME TO bot_outbox;
ALTER TABLE bot_outbox ALTER COLUMN source_chat_id TYPE text, ADD COLUMN source_platform bot_platform;
UPDATE bot_outbox SET source_platform = 'telegram' WHERE source_chat_id IS NOT NULL;

ALTER TABLE telegram_state RENAME TO bot_state;

CREATE TABLE bot_accounts (
  platform bot_platform NOT NULL,
  external_id text NOT NULL,
  user_id uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  PRIMARY KEY (platform, external_id),
  UNIQUE (platform, user_id)
);
INSERT INTO bot_accounts SELECT 'telegram', telegram_user_id::text, id FROM users WHERE telegram_user_id IS NOT NULL;
ALTER TABLE users DROP COLUMN telegram_user_id;
```

Ids are `text` everywhere. `pool.ts:4` parses `int8` as a JS number, which would corrupt Discord snowflakes (above 2^53). Telegram accepts string `chat_id`s.

Migrations run at boot (`index.ts:13`). While Render briefly runs the old and new instances side by side, only the old instance's Telegram queries can fail; `telegram_user_id` is read nowhere else. A Telegram webhook that fails gets retried by Telegram, so nothing is lost.

**Discord rules:**

- In a DM, everything is handled, as in Telegram.
- In a server channel, a message is handled only if:
  - the channel is linked to a project, or
  - the message mentions the bot, or
  - the message is `start CODE`.
  
  Anything else is ignored, so unrelated channels get no "not connected" spam.

**Linking:**
