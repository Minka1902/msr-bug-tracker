# Discussions (BUGTRK-26), AI instructions (BUGTRK-27) and custom card types (BUGTRK-25)

## Context

Three requests from Michael:

- **BUGTRK-26:** add a **Discussion** card type to Startup and Household projects. A discussion can only be closed once it has a conclusion or decision.
- **BUGTRK-27:** add instructions that AI workers get at the start and end of everything they do, "like CLAUDE.md but for MSR".
- **BUGTRK-25:** let Startup projects and Pro-plan projects add their own card types, with permissions.

Decisions made with Michael on 2026-11-01:

- **Custom card types:**
  - Available in every **Startup** project, and in **any project whose owner is on Pro**. The check uses the owner's current plan.
  - Permissions are set per role: **who can create** cards of the type, and **who can edit or move** them. Every member can still see them.
- **AI instructions:**
  - Set **per project** in Project settings → AI instructions, in two fields: **Before you start** and **When you finish**.
  - Every AI app or AI worker working in the project gets them with each MCP tool answer: start instructions first, finish instructions last.

Defaults (no decision needed):

- A custom type **works like a built-in type**: Task, Bug, Feature, and so on. It uses that type's workflow, statuses and fields, so nothing about workflows changes.
  - The built-in type is fixed once the custom type exists.
  - Deleting a custom type turns its cards back into the built-in type.
- If the owner leaves Pro, existing custom types keep working. Only adding or changing types needs the plan; deleting them is always allowed.
- The project owner can always create and edit every type. A role that lacks `task.create` or `task.edit_*` still can't, whatever the type allows.
- Comments and attachments follow the normal permissions, not the type's.
- Moving a card to another project keeps its custom type when a type with the same name and built-in type exists there. Otherwise it falls back to the built-in type.
- The decision is its own field, called **Decision** in the app and `decision` in the API. It is required while a discussion is in any `done` status.

## Global constraints

- Work on branch `claude/bugtrk-25-26-27`, with one commit per ticket.
- File layout: one component per file. Inside a file: consts, then functions, then hooks, then the return.
- No unnecessary imports, consts or comments. `snake_case` columns, `camelCase` API fields.
- Server modules have `routes.ts` (zod parsing and permission checks) and `service.ts` (SQL consts first, then functions).
- Backend favors the most efficient approach: invariants in the database where they fit, one query per check, set-based SQL.
- Move each MSR ticket to **In Progress** before its first task and to **In Review** after its push.

## BUGTRK-26: Discussion card type

**Migration `020_discussions.sql`:**

```sql
ALTER TYPE task_type ADD VALUE 'discussion';
ALTER TABLE tasks ADD COLUMN decision text NOT NULL DEFAULT '' CHECK (length(decision) <= 20000),
  ADD CONSTRAINT tasks_discussion_decision CHECK (type::text <> 'discussion' OR completed_at IS NULL OR btrim(decision) <> '');
```

`completed_at` is set exactly when a task is in a `done` status, so one row-level CHECK covers every path:

- single and bulk edits
- board drags
- AI tools and Telegram
- status category changes and status deletes
- imports

`type::text` avoids using the new enum value in the same transaction.

**Shared:**

- `TASK_TYPES` and `TYPE_META` get `discussion`.
- Startup and Household `taskTypes` include it.
- `DECISION_REQUIRED` is the error code.
- `taskFields.decision` and `TaskDetail.decision` are added.

**Server:**

- `createTask`, `updateTask` and `bulkUpdateTasks` check first, so the error is clear and names the cards: `400 Add a decision before closing WEB-3`, with `details: { code, tasks }`. The CHECK is only the safety net. The error handler maps a `tasks_discussion_decision` violation, such as a status category change or a status delete, to the same 400.
- Duplicating a card copies its decision. Recurring copies start without one.
- The demo generator never picks discussions.
- Import and export get a **Decision** column. "discussion" and "decision" words map to the type. A done discussion without a decision is imported as not done.
- MCP: `create_task` and `update_task` take `decision`, and `fetch` returns it for discussions.
- Telegram: `done KEY-12: <decision>` closes a discussion. A plain `done KEY-12` on an undecided discussion explains how to close it.

**Client:**

- A `MessagesSquare` type icon.
- A **Decision** section in the task detail for discussions.
- A reusable promise-based `usePrompt` (provider + multi-line `TextPromptDialog`).
- `useUpdateTask` catches `decision_required`, asks "What was decided?", and retries the same patch with the decision. Every way to close a card is covered: status picker, board drag, chore check-off and quick actions.
- Bulk edits show the server's message.

**Tests:**

- Server:
  - Closing without a decision → 400 with the identifier; closing with one works.
  - Bulk close lists the undecided cards.
  - Changing the type to discussion while done → 400.
  - Clearing the decision while done → 400.
  - Changing a status's category to done with undecided discussions in it → 400.
  - Duplicates keep the decision.
- MCP and Telegram parser tests.
- Client test for the prompt-and-retry.

## BUGTRK-27: AI instructions

**Migration `021_ai_instructions.sql`:** `projects.ai_start` and `projects.ai_finish`, both `text NOT NULL DEFAULT ''` and at most 4,000 characters each.

**Shared and API:**

- `updateProjectSchema.aiInstructions { start?, finish? }`, which needs `project.edit`.
- `ProjectDetail.aiInstructions { start, finish }`.

**MCP:**

- `run()` hands each tool handler a `Set` of the project ids it touched, then loads their instructions in one query and only when the set isn't empty:

  ```sql
  SELECT key, ai_start, ai_finish FROM projects WHERE id = ANY($1) AND (ai_start <> '' OR ai_finish <> '')
  ```

- The answer becomes `[start blocks…, JSON, finish blocks…]`.
- Covered tools: `fetch`, `list_tasks`, `my_tasks` (every project in the page), `create_task`, `update_task`, `add_comment`, `add_checklist_items`, the shopping tools, and calendar tools that touch a project.
- Discovery tools (`list_projects`, `search`) stay short.
- The server instructions tell the AI to follow project instructions.

**Client:** a Project settings tab **AI instructions** (needs `project.edit`) with two fields, character counts, examples and **Save**.

**Tests:**

- PATCH needs `project.edit`; over 4,000 characters → 400.
- MCP answers start with the start block and end with the finish block for `fetch`, `update_task` and `my_tasks`.
- No blocks when the instructions are empty, or for `list_projects`.

## BUGTRK-25: Custom card types

**Migration `022_card_types.sql`:**

```sql
CREATE TABLE project_card_types (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  project_id uuid NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  base task_type NOT NULL,
  name text NOT NULL CHECK (length(name) BETWEEN 1 AND 40),
  icon text NOT NULL,
  color text NOT NULL,
  create_role_ids uuid[] NOT NULL DEFAULT '{}',
  edit_role_ids uuid[] NOT NULL DEFAULT '{}',
  created_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (project_id, id)
);
CREATE UNIQUE INDEX project_card_types_name_idx ON project_card_types (project_id, lower(name));
ALTER TABLE tasks ADD COLUMN card_type_id uuid,
  ADD CONSTRAINT tasks_card_type_fkey FOREIGN KEY (project_id, card_type_id)
    REFERENCES project_card_types (project_id, id) ON DELETE SET NULL (card_type_id);
CREATE INDEX tasks_card_type_idx ON tasks (card_type_id) WHERE card_type_id IS NOT NULL;
```

The composite key guarantees a card only uses its own project's types. Deleting a type clears it from its cards.

**Shared:**

- `cardTypesAllowed(tier, module)` = `module === 'startup' || tier === 'pro'`, and `CARD_TYPES_MAX = 30`.
- `cardTypeSchema` and `updateCardTypeSchema`.
- `cardTypeAllows(roleIds, roleId, isOwner)`.
- Types:
  - `CardType`
  - `TaskCard.cardType { id, name, icon, color } | null`
  - `ProjectDetail.cardTypes` and `cardTypesAllowed`
  - `taskFields.cardTypeId`
- The type filter accepts card type ids as well.

**Server:**

- `modules/cardTypes`:
  - `POST /projects/:key/card-types`, `PATCH …/:id` and `DELETE …/:id` need `project.manage_workflow`. Create and update also need `cardTypesAllowed` for the owner's plan (402 otherwise).
  - Role ids must belong to the project. Name conflicts → 409. At most 30 types.
- `getProjectDetail` loads the AI instructions, the owner's tier and the card types in **one** extra query.
- Cards: `TASK_FROM` left-joins `project_card_types`, and `toCard` adds `cardType`.
- `LOAD_TASK` returns the card type's name and edit roles, so every edit guard can refuse with `403 Your role (X) can't edit <Type> cards`. The guards:
  - `assertCanPatchTask` and `assertCanEditTask`
  - delete, reopen and move
  - bulk edit and bulk delete
- `createTask` and `updateTask` check the target type's create roles, and take the type from the custom type's built-in type.
- Duplicating checks the create roles. Recurrences keep the type. A move remaps the type by name.
- Filters: built-in type values match cards without a custom type; ids match `card_type_id`.
- MCP:
  - `fetch` on a project lists the card types.
  - The `type` argument of `create_task`, `update_task` and `list_tasks` accepts a built-in type or a custom type name.
  - `compactTask` shows the custom name.

**Client:**

- Project settings → **Card types**: shown with `project.manage_workflow`, and to the owner when the plan doesn't allow it, as an upsell.
  - `CardTypeSettings` lists the types.
  - `CardTypeEditor` sets name, icon, color, "Works like", who can create and who can edit or move.
  - `RoleChecklist` is the reusable role multi-select. The owner role is always on.
- `TypeIcon` takes an optional `cardType`. `taskMeta` helpers return a card's type value and label.
- `useTaskOptions.type` lists the module's types plus the card types the user can create.
- Every type picker and creator sends `{ type: base, cardTypeId }`.
- `useProjectPermissions.canEditTask` also checks the card type's edit roles.
- Startup's Shop card lists "Your own card types with permissions".

**Tests:**

- Free software project → 402. Startup project → 201. Pro software project → 201.
- Member without manage_workflow → 403. Unknown role id → 400. Duplicate name → 409. 31st type → 400.
- A role outside the create roles can't create the type, or switch a card to it.
- A role outside the edit roles can't patch, move, delete, bulk edit or add checklist items, but can still comment.
- Deleting a type reverts its cards.
- Move remaps the type by name.
- The filter by type id works.
- MCP `create_task` with a custom type name works.
- e2e: create a type in settings, create a card with it, and see its icon and name.
